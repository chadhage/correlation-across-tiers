# AV23 authentication context-propagation qualification

**NOT CERTIFIED.** Logging suppression is not propagation suppression.
These bounded probes use the existing provider and local synthetic wire
receivers, never real credentials or third-party requests. Only header presence,
counts, source hashes and status are retained; no tokens, claims, keys, request
headers/values, response bodies or raw diagnostics are persisted.

**Artifact boundary:** the original Java receipts used the earlier `c3f552...`
parent-only guard. Later Netty and parent OkHttp receipts used the byte-frozen
`bb829b...` guard 1.1.0. Each receipt retains its own actual source/artifact/mode
scope, not qualification of future source changes. The harness fails closed if
the actual guard JAR does not match the current lock. No guard repackage is
needed for the user-approved header-policy change. Unchanged Node source/wire
evidence has its separate scope.

## Java: historical failures and current-source VERIFY

The installed hash-pinned Java 3.7.10 agent and current parent-safe extension were
active with the existing `azureSdk` semantic instrumentation disabled and SDK
logger packages OFF. Under a real recording root span:

| Actual path | Received | `traceparent` | Business header |
|---|---:|---|---|
| Production `JwkKeySource` JDK HTTP lookup | 1 | present | absent |
| Azure Identity managed identity SDK, local synthetic App Service endpoint | 1 | present | absent |
| Trusted JDK HTTP positive control | 1 | present | present |

This is a **local native failure** of generic authentication-path isolation.
It is not a forged header fixture, a logger inference, or an Azure Entra test.
Literal fixed-tenant HTTPS hostname behavior remains independently unqualified;
do not infer its safety from these localhost paths.

A second actual wire run set the pinned public Azure `ClientOptions` /
`TracingOptions.setEnabled(false)` on the managed-identity credential. The same
MI `traceparent` injection persisted. SDK semantic tracing options therefore
also do not establish native HTTP propagation suppression. This is a test-only
counter variant, not an invented agent setting or production tracing change.

Those historical failures led to the explicit credential/JWKS transport
isolation candidate below. The current requirement remains no context/business
headers on every protected production identity attempt and preserved trusted
API propagation. No broad business HTTP tracing disable is authorized.

The user approved `approve_okhttp` after the two-layer Netty candidate also
failed under actual BB829 guard 1.1.0, including both MI retry attempts.
The approved candidate uses official Azure OkHttp and public header controls.
The actual parent A/B retake observed production JWKS/MI retry header absence,
verified used-client origin/member binding and preserved trusted JDK parent

the upstream instrumentation-disable option was not honored.
The user therefore selected `header_isolation_only`. The ineffective switch is
removed; production no-header requirements are unchanged, identity CLIENT spans
are retained, and the raw unfiltered transport remains a recorded negative
control expected to carry native context. A fresh source/build and native
retake without the switch is required. No prior overall failed receipt is
rewritten, greened or reclassified as a pass.

## Node: observed scoped pass

This scoped native pass is not a claim about Azure tenant issuance, deployed
hostnames, resource access, telemetry completeness or certification. R2 must
